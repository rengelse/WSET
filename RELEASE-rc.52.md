# WSET v1.4.4-rc.52 – Template Switching & Rollback

Base: rc.51. No new commercial templates or renderer adapters. Existing Mal 01 rc.28.1 stays unchanged. This release is a conservative local switching workflow for compatible, registered renderers using the same server contract. It does not publish a website or mutate a remote server.

## Use
1. Save and open the website, disconnect the remote property manager, finish server transfers. Open Malbibliotek → Kontroller kompatibilitet on the selected template version.
2. Resolve blocking findings before proceeding. Choose Klargjør malbytte. WSET repeats the analysis with the exact archive digest, validates the saved project revision, hashes and copies all ordinary non-generated source files to a temporary sibling directory. Preview actual saved project content in a separate read-only frame; page/language and device selector. As with the gallery, server functions and Assistant are not run in the preview.
3. Inspect the refreshed report and file change list. Explicitly approve the reviews, existing styles and source image policy. A native confirmation separately authorizes local npm dependency installation and execution of the selected template's build scripts. Only use trusted templates.
4. WSET builds a second disposable copy of the candidate using the actual two-ZIP website generator. It verifies the generated routes and public text/section binding parity against the registered renderer. A failed dependency install, build, mapping or changed ZIP/project stops activation. The candidate and original source are not the build directory. The build is local, not an OS sandbox: trusted build scripts run with the current user's permissions. No production output is published or registered as an actual export.
5. On successful verification, WSET uses two directory renames on the same filesystem, keeping the active project path and identity. The complete old folder becomes the backup; a persistent recovery pointer allows recovery at next startup if interrupted between renames. This is not a guarantee against filesystem/hardware failure. An original backup is not deleted automatically. New export is required after switching.
6. Malbibliotek → Tilbakefør mal shows backups belonging to the active project. Restoring brings back the previous website snapshot, not just CSS. The current project is retained as a new backup first. Latest local administration metadata and publication history are retained; technical validation is reset and the dashboard marks design changes after publication. No server rollback is performed.

## File and security policy
- Source JSON bytes, all known and unknown project data, private XML, own images, local metadata, modules and ordinary project-only files are preserved. Target demo JSON and target project data are not merged. Same-path user images win over target images; case/dir conflicts block. Recognized target design/build source files may be replaced only as explicitly listed. Source-only code with no counterpart blocks. Changed/new server code blocks until a separate migration exists. Unsupported renderers and cross-category mappings remain blocked. Own typography is retained; a style-reset option and interactive manual remapping are not implemented.
- The complete prior project is retained next to the original path in `.wset-switch-<uuid>/original`, not in the configured central Backups folder. This same-volume layout permits rename-based activation; hidden sibling directories are not indexed as websites. Recovery pointer: `wset-switch-journal.json` in editor userData. Normal close/cancel removes disposable candidates. Interrupted preparation before journal creation may leave a hidden staging directory; do not remove a directory containing `original`. Source-generated `node_modules`, `dist`, `.astro`, `exports`, `preview-offline` are not copied into a new active candidate or rollback candidate; they remain in the full old snapshot. Dependencies are installed again when required. Symbolic links/junctions outside generated directories are rejected. The original project should not be externally edited during switching. The desktop app now enforces one instance per user data profile. Power loss, filesystem locks and actual Windows paths still require validation.
- Local server profile storage is path scoped and unchanged. The local project ID and metadata remain intact. No passwords are transferred into website packages. No archive code runs during catalogue, mapping or preparation. Build runs only after user approval.
